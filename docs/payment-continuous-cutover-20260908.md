# 결제 중단 없이 준비하는 오픈 전 보안 전환

> **최신 운영 상태:** 2026-09-08 사용자 승인 후 운영 반영과 최종 권한 검증을 완료했다. 아래의 미실행/미확인 표기는 배포 전 계획 당시의 기록이다. 현재 완료 여부·호환 수정·남은 실제 결제 테스트는 [운영 반영 결과](payment-production-deployment-20260908.md)를 우선한다.

사용자 확인: 고객 실거래는 아직 없고, 기존 운영 사이트에서 테스트용 NICEPAY 실제 결제·예약 연동·취소를 완료했다. 이번 주 오픈을 위해 결제를 일시 중단하는 단계는 두지 않는다. 기존 테스트 기록과 복구 기록은 보존한다.

**로컬 코드와 SQL을 아래 순서로 분리했다. 운영에는 적용하지 않았다.** 기존 버전의 실제 결제 시험은 기능 확인 이력이며, 이번 수정본의 합격 근거를 대신하지 않는다. 운영 연결·권한·실제 배포 경로를 확인하지 않은 상태에서 무중단을 보장하지 않는다.

## 변경한 구조

| 단계 | 파일 / 동작 | 기존 결제에 미치는 영향 |
|---|---|---|
| 준비 | `supabase/migrations/20260908120000_verified_payment_boundary.sql` | private 검증/시도/알림 테이블, 새 함수와 전용 역할 추가. 구 finalizer·주문 RPC의 기존 고객 권한·기존 알림 함수를 유지 |
| 인덱스 | `supabase/operations/payment-index-create-online.sql`, `payment-index-drop-legacy-online.sql` | CONCURRENTLY로 예약/TID 인덱스 생성 후 잘못된 전역 TID 인덱스 제거. 주문/TID 고유성 유지 |
| 서버 전환 | 새 메인 order/callback/approve, webhook/reconcile | 새 주문은 원래 DB 상품 가격 계산을 호출하고 같은 트랜잭션에서 private 스냅샷 등록. SDK 요청 형식과 콜백 주소 유지 |
| 권한 차단 | `supabase/operations/payment-cutover-activate.sql` | 새 서버 처리 확인 후 구 확정 RPC 차단·테이블/우회 방어·신규 알림 outbox 전환을 한 트랜잭션으로 적용 |
| 별도 정산 정책 | `supabase/operations/payment-settlement-policy-optional.sql` | 이번 오픈 전 전환에 포함하지 않음. 과거/테스트 거래 대조와 별도 승인 후에만 적용 |

준비 단계부터 새 승인 설정은 `approvals_enabled=true`다. 정상 주문 접수 권한을 회수하거나 결제 화면을 닫는 절차가 없다. 과거 중단용 `payment-cutover-close.sql`, `payment-cutover-open.sql`, `payment-safe-pause.sql`은 실행문을 제거하고 폐기 안내만 남겼다.

**준비 단계만 적용하면 기존 취약 권한이 남는다.** 새 서버 검증과 권한 차단을 마쳐야 보완이 완료된다. 고객 오픈 전에 이 과정을 마치며, 준비 상태를 장기간 운영 상태로 남기지 않는다.

## 새 주문과 기존 테스트 거래

- 새 `create_verified_payment_order`는 기존 서버 가격 계산으로 생성된 주문을 `payment_private.managed_orders`에 등록한다. 고객이 보내는 가격을 신뢰하지 않는다. 소유자·금액·상품/옵션·예약자·수단·만료 스냅샷을 승인 claim과 확정에서 다시 대조한다. 승인 요청 금액도 private 스냅샷 금액과 묶는다.
- 신규 등록 주문에만 서명된 인증 시도와 영구 claim을 근거로 승인 POST를 한 번 허용한다. 이후 불명확한 응답·재시도는 GET으로 확인한다. 스냅샷이 다르면 기존 주문 경로로 우회하지 않는다.
- 구 주문은 지연된 정상 서명 콜백이 도착해도 승인 claim이 false다. **기존 TID를 재승인하지 않는다.** 이미 DB에서 paid인 주문은 실제 GET 검증 후 기존 결과만 반환한다. 새 예약·결제·알림을 소급 생성하지 않는다.
- PG에서는 paid지만 DB가 pending인 구 주문은 고객/웹훅 경로에서 확인 대기로 남고, 관리자 인증 및 PG 재조회로 별도 확인한다. 만료/취소 주문은 자동으로 되살리지 않는다. 준비 구간의 기존 주문 스냅샷 무결성을 새 기록과 같다고 가정하지 않는다.
- 수정본에서 생성한 주문은 PG의 실제 paid 조회가 확인되면 새 인증 콜백을 다시 요구하지 않고 확정/복구할 수 있다.

NICEPAY는 인증 성공 후 승인 POST를 호출하는 [Server 승인 흐름](https://github.com/nicepayments/nicepay-manual/blob/main/api/payment-window-server.md)을 명시한다. [거래조회 문서](https://github.com/nicepayments/nicepay-manual/blob/main/api/status-transaction.md)의 ready 상태만으로 승인 전 조회가 모든 계약에서 가능하다고 가정하지 않았다. 신규 승인은 문서의 흐름을 유지하며, 구 주문에 대한 POST는 DB 등록 여부로 차단한다.

## 운영 적용 순서 — 승인 후 실행

1. **읽기 전용 확인.** 실제 운영 DB/세 사이트 연결·현재 커밋·서버 키 모델·기존 함수/ACL/트리거·마이그레이션 이력을 확인한다. 기존 테스트 승인/취소 결과와 DB 주문/예약/결제를 대조한다. NICEPAY 취소가 끝났다는 사실만으로 DB 예약도 취소됐다고 추정하지 않는다. 데이터 삭제·상태 변경·재발송은 하지 않는다.
2. **전체 스키마로 사전 연습.** 분리 SQL, 실제 알림 트리거·Edge·process-refund, 서로 독립된 DB 연결의 잠금/중복 처리, 세 사이트 표시를 확인한다. 새 버전과 같은 보안 경계를 사용하는 이전 안정 빌드를 롤백 대상으로 확보한다.
3. **준비 SQL과 인덱스만 적용.** 준비 SQL은 2초 lock_timeout, 30초 statement_timeout을 사용한다. 잠금을 얻지 못하면 해당 트랜잭션을 롤백하고 기존 서비스를 유지한 채 다시 일정을 잡는다. 인덱스 명령은 한 문장씩 autocommit으로 실행한다. BEGIN이나 여러 문장을 한 번에 보내는 드라이버 실행에 넣지 않는다. 실패 후 invalid 인덱스 유무를 확인한 뒤 재시도를 결정한다.
4. **새 서버를 검증하고 전환.** NICEPAY v1 Server/Basic 운영 키·공개 SDK key 일치를 확인하고 서버 비밀키를 설정한다. 먼저 제한된 검증 경로에서 새 주문 생성→인증→실제 승인→예약 표시→취소까지 승인된 테스트를 완료한다. 운영 메인 주소·콜백·웹훅·구 배포 URL을 같은 검증 서버로 연결한다. 구 서버와 신 서버에 승인 POST를 복제하지 않는다. 기존 결제 경로를 먼저 닫아 두는 작업은 없다.
5. **남은 구 테스트 요청 확인.** 구 승인 API 요청, 열린 테스트 결제창, pending 시도와 지연 콜백이 처리됐는지 확인한다. 단순히 15분이 지났다는 이유로 완료 처리하지 않는다. 불명확한 건이 있으면 새 권한 차단 적용을 미루고 기존 서비스를 유지한다. 고객 오픈은 보안 전환 완료 후다.
6. **취약 권한 차단.** 운영자가 새 서버와 구 테스트 요청 처리 완료를 확인한 후 동일 DB 세션에 `damda.payment_server_revision=verified-v2`, `damda.payment_test_traffic_drained=true`를 설정한다. activate SQL은 이 확인값과 인덱스 준비가 없으면 변경 없이 실패한다. 확인값은 실제 배포를 검사하는 자동 감지기가 아니며, 사람이 확인한 증거를 대신하지 않는다. 승인/주문은 계속 활성 상태다. 차단 후 `assert_payment_boundary()`와 read-only preflight로 실효 권한을 확인한다.
7. **알림 전환.** 준비 중에는 기존 알림 함수/Edge가 발송한다. activate 이후의 신규 유료 예약은 outbox에 저장된다. 기존 pg_net 요청의 처리 및 발송 기록을 확인한 뒤 새 paid 인증/claim Edge를 배포하고 새 worker를 연결한다. 새 Edge를 먼저 배포하면 기존 요청이 거부될 수 있으므로 순서를 바꾸지 않는다. 이 짧은 구간의 신규 알림은 outbox에서 대기하며 결제·예약 생성은 계속된다. 취소 알림 목적지와 실제 process-refund 연동도 확인한다.

**일괄 supabase db push 금지.** 미추적/미적용 SQL 중 `20260906001000_lock_down_payment_finalizer.sql`은 구 경로를 먼저 차단하는 초안이다. 현재 승인 계획은 위 준비 SQL과 검토한 운영 SQL만을 대상으로 한다. 파일 이름 순서대로 전체 실행하면 이번 전환 순서가 깨질 수 있다. 기존 초안은 임의 삭제하지 않았다.

인덱스 준비 확인은 이름만 보지 않고 `pg_get_indexdef`와 predicate도 대조한다. 새 인덱스는 payments(reservation_id, pg_tid)의 NICEPAY/non-null 조건이어야 하고, payment_orders(pg_tid)의 고유성은 전체 주문에 적용돼야 한다. 이름이 같더라도 정의가 다르면 자동 재사용하지 않는다.

## 장애와 롤백

준비/activate의 잠금 실패는 해당 트랜잭션만 롤백한다. 새 서버 전환 전에 실패했다면 기존 경로로 서비스하며 원인을 해결한다. activate 이후에는 미리 검증한 호환 서버 빌드로 전환하고 DB 증거·중복 방지·일반 역할 차단을 유지한다. 구 취약 finalizer 권한을 다시 열거나 영구 승인 claim을 지워 재승인하지 않는다.

알림 결과가 불명확하면 발송 로그를 확인한다. outbox/수신자 claim을 삭제해 자동 재발송하지 않는다. 과거 기록을 검증 원장에 일괄 등록하거나 고객 정산 대상으로 바꾸지 않는다. 전체 과거 매출을 막는 정산 정책은 이번 필수 적용에서 분리했다.

## 로컬 검증과 남은 확인

회귀 시험은 실제 구 finalizer와 기존 서버 가격 계산 함수를 PostgreSQL fixture에 로드한다. 준비 중 구/신 확정, 차단 후 새 주문·확정, 잘못된 준비 상태에서의 원자적 적용 거부, 가격 스냅샷 변조 거부, 기존 TID 재승인 방지, 취소 테스트 기록/기존 알림 보존을 확인한다.

PGlite 테스트는 로컬 SQL 의미와 권한을 확인하며 운영의 독립 세션 잠금·실 NICEPAY·실 pg_net 발송·Edge 런타임을 증명하지 않는다. 자세한 결과는 [결제 보안 보고서](payment-security-20260908.md)에 기록한다. **운영 중단·배포·권한 변경·추가 실제 결제/취소는 모두 미실행이다.**
